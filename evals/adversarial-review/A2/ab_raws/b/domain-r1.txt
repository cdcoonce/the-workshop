I found three concrete git-mechanics defects in `sync_boundary_squash.py`, all falling squarely in the ancestry-test/prefix-boundary/squash-base-pick lens.

**Finding 1 (line 115):** `classify_pushed_prefix` returns `first_unpushed + 1` instead of `first_unpushed`. This breaks the function's own parametrized unit tests in 4/6 cases (e.g. `classify_pushed_prefix([True, False, False])` yields 2, not the expected 1). Concretely, for a session `[c1 pushed, c2 unpushed, c3 unpushed=wrap-up]`, the inflated prefix makes `report.unpushed` compute to 1 instead of 2, tripping the "only one unpushed commit; nothing to collapse" no-op branch — the two genuinely-unpushed commits never get squashed at all.

**Finding 2 (line 207):** `pushed_flags = [_is_ancestor(remote_head, sha) for sha in session]` has the arguments backwards. `_is_ancestor(ancestor, descendant)` tests whether the first commit is an ancestor of the second; testing "is `sha` already on the remote" requires `_is_ancestor(sha, remote_head)`, not the reverse. Concrete failure: session `[c1 (pushed), c2, c3]` with `remote_head == c1`. Since c1 is an ancestor of every later commit, `_is_ancestor(c1, c2)` and `_is_ancestor(c1, c3)` both evaluate True, so every commit — including the two never pushed — is classified as pushed. `unpushed` becomes 0, the script reports `none`, and nothing is squashed. This directly contradicts the PR's own acceptance test `test_pushed_first_commit_is_not_rewritten`, which asserts `pushed == 1` and `unpushed == 2` for exactly this scenario.

**Finding 3 (line 168):** The PR body and `tests.md` describe a guard that skips the squash on staged-but-uncommitted changes, and `test_staged_uncommitted_changes_skip_squash` plus a teeth.json mutant both exercise it, but `squash()` never implements this check — control flows straight from the merge-commit guard into the `rev-list --reverse` computation with no `git diff --cached` check anywhere in the function. Concrete failure: stage an unrelated file before running the script with 2+ unpushed session commits; since `reset --soft` leaves the index untouched, the staged content silently rides along into the new squashed commit via `commit -C <old HEAD>` (which commits the current index) — uncommitted work gets swept into history instead of blocking the squash.
