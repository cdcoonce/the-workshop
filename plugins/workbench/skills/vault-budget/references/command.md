# /budget — Claude API spend / subscription-value meter

Run the budget engine and present it. The script does all the heavy lifting (scans every local Claude Code transcript, dedups by API call, computes cost by model × published rates); this command just runs it and interprets.

**Arguments:** $ARGUMENTS — optional `--month YYYY-MM`, `--budget N`, `--context work|personal`.

## Procedure

1. Run: `python3 "<engine>/budget_burn.py" $ARGUMENTS` (add `--json` if you need the structured numbers).
2. Present the output as-is, then add one line of interpretation:
   - **Personal (subscription, value-meter):** this is API-equivalent value the flat subscription delivered — no per-token cap. Frame it as "what your subscription is worth," not a budget to fear.
   - **Work (enterprise, gate):** spend against the ~$350 enterprise cap. If projected month-end is over cap, flag it and point at the lever (below).
3. **Always surface the Opus %** — it's the conductor-health metric (see the Operating Model in root `CLAUDE.md`). High Opus % = lots of judgment-and-retrieval still bundled on the expensive model; the lever is delegating bulk reads to Sonnet/Haiku workers. Low Opus % = the conductor discipline is working.

## Ledger by session and agent

For "where did it go" rather than "how much", run `python3 "<engine>/cost_ledger.py" [--since YYYY-MM-DD] [--until YYYY-MM-DD] [--json PATH] [--meter-usd N] [--export-aggregates PATH] [--fixed-weight] [--calibration PATH] [--projects-root DIR]`. Both dates are inclusive and judged on the UTC date of each call's own timestamp (a `Z` or numeric-offset ISO-8601 string; one that cannot be parsed is undated and counted, not windowed); with neither flag the window is the current calendar month. A malformed date, `--since` after `--until`, a `--projects-root` that is not an existing directory, or a `--json` path that cannot be written exits 2 with one stderr line; a bad window or root writes nothing.

It prints the window, the window total, the main-versus-subagent split in dollars and percent, subagent dollars by agent type and by model, the ten most expensive sessions, a `Largest sessions` section covering the same ten (first, median and maximum context per main-thread call, and the dollars spent above 200,000 tokens of context), a `Cost by trigger` section (dollars by the kind of user turn that preceded each call, with the part that followed a tool result, summing to the window total), a skills table (the fifteen skills with the most dollars, ties by name, then one `N more skills` line (`1 more skill` for one) summing the rest, then an always-present `(unattributed)` row (parenthesised so a skill literally named `unattributed` cannot print the same label) with its percent of the window total, then a line saying skill rows are a lower bound because the invoking call and later-turn work are not counted), one coverage line (files found, read and skipped, malformed lines, undated calls), and, only when there are any, the models it could not price. Undated calls are excluded from every figure and counted on the coverage line. `--json PATH` also writes one row per session with one row per agent inside it (the main session and each subagent, typed from its `meta.json`, else its attribution, else `unknown`); it also writes one row per skill with `sessions`, and an `unattributed` object, which together sum to the totals (a call's skill is its own record's `attributionSkill`, taken exactly as written); two runs over the same files and window write byte-identical files. Prices come from the same table `budget_burn.py` uses, so totals agree. Every field of the JSON is documented in [cost-ledger-schema.md](cost-ledger-schema.md) (schema version 7).

### Meter check and recorded cost

`--meter-usd N` takes the dollar figure you read by hand from Claude Code's usage view for the same window. N must be a finite number greater than 0, else the command exits 2 with one stderr line and writes nothing. The report then starts with a meter block (ledger total, meter figure, signed difference as ledger minus meter, gap percent), and when the gap percent, rounded to six decimal places, is strictly more than 10, in either direction, a `METER GAP` line above it; exactly 10 percent does not flag. The JSON gains a top-level `meter` (`null` without the flag).

The recorded-cost check runs on every report with no flag: it compares whole-session ledger dollars with the cumulative cost Claude Code records in the session file, for the sessions where the two cover the same calls, and prints one line for those sessions and, when there are any, one line for sessions whose recorded cost includes a model Claude Code could not price (reported, not compared). It never prints a warning and never changes the exit code. The comparability conditions are in [cost-ledger-schema.md](cost-ledger-schema.md).

### Aggregates-only export

`--export-aggregates PATH` writes a second JSON file meant to be shared: totals, per-model and per-agent-type dollars, skills, the unattributed bucket, the cost-by-trigger rows, the spread of per-session dollars (min, quartiles, max), coverage counts, unpriced models, the meter block and the recorded-cost check. Sorted keys, 2-space indent, trailing newline, dollars rounded to six places, byte-identical across runs; an unwritable path exits 2 with one stderr line, and when both `--json` and `--export-aggregates` are given and either cannot be written, neither file is written or changed. It is built from an allow-list and holds no project key, path, session id, agent id or call timestamp, and no text from any record except model names, skill names and agent type names, which it carries as written. Read those names before sharing the file: a skill or agent type name chosen by you or a plugin appears verbatim.

### Fixed weight

`--fixed-weight` adds an estimate of what the fixed context cost: the system prompt, the tool schemas and what your setup injects (skill and agent listings, instructions, hook context, MCP servers), which every call of a session sends again. The report gains a `FIXED WEIGHT` section, and the JSON gains a filled `fixed_weight` object (`null` without the flag, in which case no estimation work is done). Each transcript file, main session or subagent, is sized in characters from its own records, converted to tokens at 3.7 characters per token times a calibration factor, and charged per call at the rate that call paid: the cache-write rate when the call wrote at least that much to the cache, else the cache-read rate, never more than the call's own dollars. The costing rule, the two groups (`setup`, the upper bound on what removing your setup would save, and `claude_code`, present regardless) and every field are in [cost-ledger-schema.md](cost-ledger-schema.md). The section opens with the line `UNCALIBRATED ESTIMATE` until a calibration file supplies a factor; the section ends in a verdict against the bar fixed on 2026-11-14 (the setup is worth changing only if removable fixed context is 20% or more of window spend): `CUTTABLE`, `CANNOT FIT`, `UNDECIDED` or `NO DATA`, prefixed `PROVISIONAL` until a calibration file supplies a factor. The `fixed_weight.verdict` block in the JSON carries the same figures.

`--calibration PATH` names a JSON file with a finite `factor` greater than 0, optionally with `low` and `high` (both or neither, each finite and greater than 0, `low <= factor <= high`) and the provenance keys `date`, `claude_code_version` and `runs_per_arm`; other keys are ignored. With a calibration file the estimate is also re-run at factor 1.0 and at `low` and `high`, the report shows the setup share uncalibrated and calibrated side by side, the range, and the calibration's date, runs and version, and the JSON gains `fixed_weight.comparison` and `fixed_weight.calibration` (see [cost-ledger-schema.md](cost-ledger-schema.md)). The file is made by `python3 "<engine>/fixed_weight_calibrate.py" --full ID [ID ...] --bare ID [ID ...] [--projects-root DIR] [--out PATH] [--min-runs N] [--claude-code-version V] [--date D]` from matched fresh sessions with and without the workbench plugin; the procedure is in [cost-ledger-calibration.md](cost-ledger-calibration.md). Without the flag the file is `~/.workshop/cost-ledger/cost_ledger_calibration.json` (one location, outside the plugin install, so it survives plugin updates; no other directory is consulted). With no flag, an absent file at that default path means factor 1.0, uncalibrated; a path you name with `--calibration` that does not exist exits 2 with one stderr line and writes nothing (a typo must not give uncalibrated numbers quietly). A file that exists but is unreadable, is not an object, or has a missing or invalid `factor` exits 2 with one stderr line and writes nothing. `--calibration` does nothing without `--fixed-weight`. The aggregates export carries `fixed_weight` unchanged; it holds only fixed component names and numbers.

## Notes

- The number is **machine-local** — it reflects this machine's Claude Code usage only. The work/enterprise $350 gate only means something on the work machine; on personal it's a value meter.
- Rates and the dedup-by-`requestId` fix live in the script. If the number looks implausible, suspect a rate change or a transcript-format change — verify against Claude Code's own `/cost` for a single session before trusting a big swing.
