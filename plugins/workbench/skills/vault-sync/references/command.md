# /sync — Manual Git Sync

Manually trigger git synchronization. Useful when switching machines or wanting to sync mid-session.

**Concurrency model:** the vault is written by N same-day Claude sessions _plus_ two machines — on busy days five or more sessions each write the same four accumulating hub files before pushing, hours apart. Divergence at sync time is therefore normal, not exceptional: expect the remote to have moved, and expect conflicts on the hub files to be structural (every session inserts at the same anchors per workshop #871), not a sign anything went wrong.

## Usage

```
/sync          — commit and push the intended changes
/sync pull     — pull latest from remote (with rebase)
/sync status   — show git status without syncing
```

## Process

### Push (default)

1. **Declare the intended files, then run the vault-health durability gate immediately before staging:** review both staged and unstaged changes and name exact vault-relative file paths, including both endpoints of a rename. Never infer intent from all dirty paths. If any staged path is outside that list, stop without resetting or unstaging it. The current health gate checks the whole working tree, so also stop if any other changed path is outside the list: an uncommitted foreign note could otherwise make a link check pass for a commit missing that note. Coordinate the unrelated work instead of widening the list automatically. Run `uv run --script ci/vault_health.py`; if it fails, times out, or cannot run, leave all edits uncommitted and do not pull or push. A vault without this script remains compatible and may proceed. **When the session touched a hub file** (`brain/Gotchas.md`, `brain/Key Decisions.md`, `perf/Brag Doc.md`, `.brain/handoff-*.md`), also run `python3 "<skill>/scripts/entry_replay.py" --lint` after the health gate and before staging: it checks that every ledger block and handoff still parses under the entry-replay grammar (no undated heading at entry level, no mixed entry kinds or levels, no dated entry outside an anchor block, no duplicate handoff `##` headings), needs no git and no network, and exits 1 on any finding (a duplicated anchor path and an unclosed code fence are findings too; a named path that is missing or is not a hub file is a finding, and checking nothing fails). A finding means the entry's shape is wrong — fix the entry first, then re-run; a hub file that does not lint is one the replay would refuse at the next conflict.
2. Recheck scope after the health gate, then stage only the intended changed files with literal pathspecs. Already-staged deletions need no additional `git add`. Scope means whole working-tree files, including unstaged portions of a selected file; do not silently interpret it as preserving partial staging.
3. Generate a descriptive commit message from the changes
4. Use a path-limited commit: `git --literal-pathspecs commit --only -m <message> -- <intended changed paths>`. This keeps unrelated files staged by another process out of this commit.
5. **Resolve the sync target, then `git pull --rebase origin <target>` first.** Run `python3 "<skill>/scripts/sync_target.py"` and read `target` from its JSON: the remote branch this checkout's work integrates into. It is **not** the current branch's name. In a desktop-app worktree on an unpublished `claude/*` branch (or a detached HEAD) it is origin's default branch (`source: remote-default`), because that branch name exists nowhere on the remote. Exit 1 (`error`) means nothing resolved: stop and alert the user. Under the concurrency model above (N same-day sessions plus two machines) the remote has usually moved since this session started, so rebase onto the target _before_ pushing instead of letting the push get rejected. If the rebase conflicts: abort it, then check the entry-replay fallback below — if every conflicting file is on its allowlist, run the fallback; otherwise list the conflicting files and alert the user. Never auto-resolve by hand (the one exception, a user-approved rebuild after a refusal, must pass `--verify` before it is pushed — see below).
6. Run `git push origin HEAD:<target>` to sync with remote. Never accept git's `--set-upstream origin <branch>` hint for a session branch: it publishes a stray `claude/*` branch that no other session or machine pulls, which is how the 2026-09-10 and 2026-09-20 wrap-ups were stranded off `main`.

The compatibility helper `session-stop.py` requires `--explicit-sync` and one
`--path <vault-relative-file>` per intended file; without paths it refuses before
running Git. Lifecycle Stop hooks do not supply authorization. Its Python
`push(..., intended_paths=...)` API treats an empty list as a no-op; only direct
Python callers omitting that argument retain the legacy all-changes behavior.
The scope limits the new commit, not existing local commits a push may publish.
It does not isolate concurrent edits to the same files or rebase/index activity;
coordinate or isolate an actively shared checkout.

### Entry-replay fallback (allowlisted hub files only)

When the aborted rebase's conflicts are confined to the four accumulating hub files — `brain/Gotchas.md`, `brain/Key Decisions.md`, `perf/Brag Doc.md`, `.brain/handoff-*.md` — run the scripted replay instead of escalating immediately:

```bash
python3 "<skill>/scripts/entry_replay.py" --base <commit before this session's first commit> --json
```

`<skill>` is this skill's announced base directory (the directory holding SKILL.md); `--base` is the same session base the wrap-up audit and the #892 sync-boundary squash use. The three-way base the replay actually merges against is `git merge-base HEAD <origin head>`: a session that already pushed some commits mid-session shares them with origin, and reading them as additions on both sides would replay a pushed entry next to its own later correction. `--base` only has to be an ancestor of (or equal to) that merge-base, else the replay refuses (the report's `merge_base` names it). The script trusts nothing from the caller: it resolves the sync target itself (the same rule as `sync_target.py`), re-fetches it from origin, re-derives both sides' changes from the base, and re-checks the allowlist itself, so running it on a mis-diagnosed conflict is safe — it refuses.

What it does (issue #893, codifying the vault's `3164dec0` hand-built union):

- Builds the merged result on a fresh branch from fetched `origin/<target>`, starting from **origin's copy** of every file, and carries the session's non-conflicting changes along. Only the session's own local branch is moved to the result; local `main` belongs to the primary checkout and is never touched. On a detached HEAD (Codex runs vault sessions in detached worktrees) no branch moves at all: HEAD is left detached at the result.
- **Ledger rule** (Gotchas, Key Decisions, Brag Doc): the session's change is read per anchor block as _whole entries_ — new entries, and entries edited in place (an in-place correction like the vault's `2455bf8c`, including an edit that changes the entry's own heading line while its date and most of its text stay — overwriting an entry with a different one counts as a deletion). Each entry the session edited must be byte-identical, exactly once, in origin's copy of the block (the per-replaced-entry assertion); origin's entries the session did not touch simply win, corrections included. New entries are added unless origin already holds them. **Nothing is re-sorted**: origin's entries keep their exact order (real blocks are not uniformly ordered, so a block-wide sort would rewrite entries the session never touched), an edited entry keeps its origin position, and each new entry is placed **positionally, not by date**: immediately after the session's predecessor entry (the nearest earlier entry of the session's block that origin also holds), which must appear on origin exactly once byte-identical — else immediately before the session's successor entry under the same requirement, else the replay refuses. A new entry that opens the session's block goes to the top of origin's block, directly under the preamble (so when both sides insert at the top, both survive and the session's sits first). New entries sharing a position keep the session's order. A correction both sides made identically (origin already holds exactly the session's edited entry) is already applied; origin holding both the base version of an edited entry and a byte-identical copy of the edit refuses (replacing would leave the edit twice). **Amend guard:** a new session entry that pairs with an entry _origin added_ since the merge-base refuses ("the session re-adds an entry origin already has in a different version — was a pushed commit amended or rebased?"): origin keeps the pushed version, the session re-adds the corrected one, and replaying both would put it in twice. The pairing ignores the date, because an amend can re-date the entry: whatever the same-day similarity rule pairs, plus — on any day — the same heading text after the date, or two bodies of at least 60 characters that are at least 90% alike (short boilerplate such as `**Decided:**` is shared by unrelated entries of different days). Anchored insert (#871) stays the write-time rule. An anchor is a block's innermost non-entry heading, so the Brag Doc's `### Wins` and `### Growth` sort separately. Entry headings may carry a trailing qualifier — `(2026-10-10)`, `(2026-10-10, [[proj]])`, `(2026-09-14 onward, [[x]])` — and a dated `- **YYYY-MM-DD` bullet inside a heading entry is body text, not an entry. Deleting an entry, editing a block preamble, or changing any text outside the anchor blocks refuses. The output is **spliced, not re-serialized**: origin's raw lines with only the session's entries replaced or inserted, so the preamble and every untouched entry stay byte-identical, **Separator semantics:** blank lines are the session's wherever the session wrote them — a new entry ends with the blank lines it ended with in the session's file, the entry before an insertion (or the preamble, for one at the top of a block) takes the blank lines the session had before the new entry (never a neighbour's, so a new entry is neither glued to a neighbour that lacked a trailing blank nor loosens a tight list), and an entry the session kept or edited keeps origin's trailing blank lines unless only the session changed them. A leftover base/tip entry pair counts as an edit only when it is the unique similar match — same date, and the same heading text, a mostly unchanged body, or (for a one-line bullet) a mostly unchanged start line. #871's ordering-drift detector (#874) stays on as the order tooth for what sessions write: the replay no longer sorts, so it is the only place a misordered entry is caught.
- **Handoff rule**: origin's file wins wholesale; inside each `##` section this session touched (the `handoff_sections` collector's section model), the replay is **item-level** — an item is a top-level `- ` bullet with its indented continuation, or a blank-separated paragraph. Base items are aligned to origin's by _position_, not content (two identical `- Links: [[x]]` bullets under different topics are different items): every item the session replaced must be unchanged and aligned on origin, and an inserted item lands right after its aligned base predecessor, keeping the session's own blank-line separators (a paragraph appended after another stays blank-separated; tight bullets stay tight); an item origin itself added _in the same gap_ is not inserted twice (an item that merely resembles an existing one, or one origin added elsewhere, is kept), and the same holds for the end of a replacement against the gap just after the replaced run. **Handoff amend guard:** a session-inserted item that is a _version_ of one origin inserted in the same gap — identical first line, one text opening the other's, or at least 90% alike, but not identical — refuses ("was a pushed commit amended or rebased?"): the pushed version and the corrected one would both land. **Move = edit:** a base item the session deleted and a tip item it inserted elsewhere in the section that read as versions of one another (identical first line, one text opening the other's, or at least 60% alike) are one move, or move-and-edit; the item must be unchanged and aligned on origin like any replaced item, else the replay refuses ("moved and edited") — an origin that deleted the item would otherwise see the delete as already applied while the new copy resurrected it. A move origin made identically stays already applied. **Separator semantics:** an inserted item keeps its own separators, the item before an insertion, a deletion or a replacement takes the separator the session gave it (deleting `- b` from `- a`, `- b`, blank, paragraph leaves a blank before the paragraph rather than gluing it to `- a`), and an item the session left in place keeps origin's separator unless only the session changed it. Items compare ignoring trailing blank lines, both sides making the same delete or the same edit counts as already applied, a changed item with a byte-identical twin in a section origin also changed refuses, and lines inside a code fence stay in their item. Two wrap-ups editing different bullets of the same section both survive. The `_Updated …` stamp line is not a preamble divergence: it resolves three-way (the session's if the session changed it, else origin's), while any other preamble divergence on both sides still refuses. The session's `description:` clause is re-applied **additively** — origin's paragraph plus the session's added clauses, never the session's whole rewritten paragraph. Sections both sides renamed identically (the session's section-name list equals origin's and differs from the base only by renames at the same positions) are matched by position; any other added, removed, or reordered section refuses.
- **Assertions, fail-closed**: before every replacement it asserts origin's corresponding span is byte-identical to the session-base version, with spans drawn _per replaced entry / per replaced item_ — exactly the spans the replay replaces, never wider and never skipped (narrowness is spec). Any assertion failure, any entry deletion, a file ending inside an open code fence, or any conflict outside the allowlist → it stops and restores the repository. **Self-verification:** before anything is written, the merged text of every file is re-checked against both sides with the same line-multiset comparison `--verify` uses; a merge that loses or duplicates a line refuses (`self-check: …`, first lines quoted) — there is no flag to skip it. Two structural invariants cover what a line multiset cannot see (it ignores blank lines and accepts one copy of a line both sides added). **Exactness (S1):** for every handoff `##` section and every ledger anchor block, when origin's copy equals the session base's, the merged unit must be byte-identical to the session's; the merge functions assert it (`structural self-check: section/block X differs from the session's although origin did not change it`) and it must never fire on a correct merge. **Item/entry level (S2):** every unit the session touched is re-split with the same item/entry splitter the merge uses, and every merged item's content (trailing blank lines ignored) must consume one occurrence of an item origin or the session holds (an item both sides kept from the base counts once); an item neither side wrote — two items glued by a lost blank line, an entry whose lines landed under another — refuses (`structural self-check: merged section X contains an item neither side wrote`). Only two handoff lines are resolved by rule instead of counted — the frontmatter `description:` and the body-preamble `_Updated` stamp (before the first `## `) — and each must hold exactly the version the merge rule chooses (stamp: the session's if it changed it, else origin's; description: origin's if the session left it alone, the session's if origin did, else the clause merge); in any other file, or anywhere else in a handoff, such lines are ordinary lines. Every conflicting file is evaluated before it stops, so the report's `refusals` lists each one (`[{"path", "reason"}]`; `reason` stays the first). An exception the merge functions do not anticipate is a refusal too (`internal error while merging <path>: <type>: <msg>; escalating`) with the JSON report and the repository untouched, never a bare traceback. The escalation path is unchanged.
- Runs `uv run --script ci/vault_health.py` on the replayed tree before anything is pushed; a failure restores the original state.

Read the outcome, don't infer it: `replayed` (exit 0) means HEAD — the session's local branch, or a still-detached HEAD (the report's `branch` is `null`) — now sits on the tip of `origin/<target>` (the report's `target`) and step 6's `git push origin HEAD:<target>` is a fast-forward — proceed. `none` (exit 0) means the fallback had nothing to do — proceed exactly as today. `refused` (exit 1) means a fail-closed guard fired — including an in-flight rebase, merge, or bisect — and the repository is already restored to its original branch or detached commit; list every file in the report's `refusals` (not just `reason`), alert the user, and never re-attempt the merge with hand-rolled git commands. **A user-approved hand rebuild after a refusal is the one exception** — and it must pass `python3 "<skill>/scripts/entry_replay.py" --verify --base <session base> --tip <session tip> --origin <origin head> --result <rebuilt commit>` before anything is pushed. `--verify` compares the multisets of non-blank lines for every path either side or the result touches: the result must hold every line exactly `base − deletions + additions` times, so an addition lost, *untouched content lost*, or a line held too often (a duplicated sentence inside a modified line is the classic) fails it with exit 1; it also re-splits every unit the session touched with the same item/entry splitter and fails an item neither side wrote (the report key `glued`). The handoff's `_Updated` stamp and frontmatter `description:` are resolved by rule (the same rule as the replay: the stamp must be the session's if the session changed it, else origin's; the description must be origin's, the session's, or the clause merge, whichever the rule picks) and are reported under `resolved`. If origin already holds later commits of the same session (a mid-session push), `--verify` compares against `merge-base(tip, origin)` instead of `--base` and says so. **Do not push on a failure** — fix the rebuild and re-run.

### Pull

1. Resolve the sync target as in Push step 5, then run `git pull --rebase origin <target>`
2. If conflict: abort rebase, list conflicting files, alert user
3. If success: report what was pulled

### Status

1. Run `git status` and `git log --oneline -5`
2. Report: uncommitted changes, untracked files, recent commits

## Constraints

- Never auto-resolve merge conflicts by hand. The only scripted resolution is the entry-replay fallback above; a user-approved hand rebuild that follows a refusal must pass `entry_replay.py --verify` before it is pushed
- Never force-push
- Forward references are allowed during editing, but every wikilink must resolve before the health gate permits commit/sync. "Banked as/in `[[X]]`" means `X` exists or is created, linked, and indexed in the same durability transaction.
- Push always rebases onto the remote first (see step 4) — don't rely on the reactive "pull if rejected" path
- **Never let a regenerable derived artifact into the synced vault.** Counters, indexes, caches, and frequency maps (e.g. a term-frequency tally) conflict on every sync because git can't merge two diverged counters. They're regenerable state, not source of truth — keep them machine-local (gitignored) and let each machine rebuild. If a conflict keeps recurring on the same _generated_ file, that file should be untracked, not repeatedly merged. **This rule is scoped to regenerable state.** The hand-authored accumulating ledgers (Gotchas, Key Decisions, Brag Doc, the handoff) are source of truth: they stay in git and merge by entry-replay (the fallback above) — never by untracking them, and never by `.gitattributes merge=union`, which reports no conflict and silently mangles in-place entry corrections. See `brain/Gotchas.md`.
- Show clear error messages on failure
